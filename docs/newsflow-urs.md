# 사용자 요구사항 명세서 (URS)

**시스템명** 뉴스 스크랩 자동화 시스템 (NewsFlow)
**문서 버전** 0.2 — 1주 스프린트 범위
**변경 사유** v0.1(요구사항 85개)을 2인 · 1주 개발 가능 범위로 축소
**작성 근거** 기존 n8n 워크플로 `테스트3(수정1)` 분석

---

## 1. 이번 릴리스의 목표

> **n8n 워크플로를 자체 시스템으로 대체하고, 매일 아침 자동으로 뉴스 메일이 오게 한다.**

부가 목표는 두 가지다.

- 이전에 보낸 기사가 다시 오지 않게 한다 (n8n에서 안 되던 것)
- 설정을 스프레드시트가 아닌 화면에서 관리한다

이 세 가지가 되면 1차 릴리스는 성공이다.

### 1.1 개발 조건

| 항목 | 내용 |
|---|---|
| 기간 | 7일 |
| 인원 | 2명 (백엔드 1, 프론트엔드 1) |
| 검증 기준 | 기존 n8n 워크플로 결과와의 비교 |

### 1.2 우선순위

| 표기 | 의미 |
|---|---|
| **M** | 필수 — 이번 릴리스에 반드시 포함 |
| **S** | 여유 시 — 6~7일차에 시간이 남으면 |

v0.1의 C(선택) 항목은 전부 **범위 외**로 이동했다. 2절 참조.

## 2. 이번 릴리스에서 제외한 것

축소가 이 문서의 핵심이므로 먼저 명시한다.

| 제외 항목 | v0.1 ID | 제외 사유 |
|---|---|---|
| 워크플로 시각 편집기 | UR-WFL-03~07 | 최소 3일 소요. 없어도 자동화는 동작한다 |
| 처리 단계 추상화 구조 | UR-WFL-01~02 | 내부 구조 개선. 동작에 영향 없으므로 이후 리팩터링 |
| 복수 워크플로 | UR-WFL-06 | 1차는 고정된 처리 흐름 하나만 제공 |
| 계정 · 로그인 | UR-ACC-01~02 | 단독 사용 전제. 배포 시 재검토 |
| 기사 요약 생성 | UR-PRC-07 | 외부 API 비용·지연 예측이 어려움 |
| 통계 화면 | UR-STO-05 | 데이터가 쌓인 뒤에 의미가 있음 |
| 기사 자동 정리 | UR-STO-06 | 초기에는 데이터가 적음 |
| 이메일 외 전달 수단 | UR-DLV-07 | 메일 하나로 충분 |
| 실패 실행 재실행 | UR-EXE-08 | 수동 실행으로 대체 가능 |
| 정렬 기준 변경 | UR-PRC-06 | 고정 정렬로 시작 |

### 2.1 제외했지만 구조는 열어둘 것

다음은 이번에 만들지 않지만, **나중에 붙일 때 기존 코드를 갈아엎지 않도록** 설계 단계에서 고려한다.

- 처리 흐름을 함수로 구현하되 단계별로 함수를 분리한다 → 이후 노드 추상화가 쉬움
- 기사 테이블에 요약 컬럼을 미리 두고 비워둔다 → 이후 요약 기능 추가 시 마이그레이션 불필요
- 모든 조회에 사용자 구분 컬럼을 둔다 → 이후 계정 기능 추가 시 스키마 변경 불필요

## 3. 용어

| 용어 | 정의 |
|---|---|
| 피드 소스 | 기사를 수집할 대상. 표시명과 주소 템플릿을 가진다 |
| 키워드 | 검색어. 피드 소스와 조합되어 실제 수집 주소를 만든다 |
| 수집 | 키워드 × 피드 소스 조합으로 기사를 모아 메일로 보내기까지의 처리 |
| 실행 | 수집이 한 번 수행된 단위. 이력이 남는다 |

## 8. 검증 기준

기존 n8n 워크플로가 정답지 역할을 한다.

| ID | 검증 항목 | 판정 기준 | 관련 요구사항 |
|---|---|---|---|
| AC-01 | 수집 결과 동등성 | 동일 설정에서 기존 워크플로와 수집 기사 목록이 일치 | UR-COL 전체 |
| AC-02 | 메일 형식 | 표 구성과 항목이 기존 메일과 동일 | UR-DLV-02~05 |
| AC-03 | 정렬 순서 | 키워드 → 소스 → 발행일시 순서 일치 | UR-PRC-04 |
| AC-04 | **중복 제거** | 연속 2회 실행 시 두 번째에 신규 기사만 전달 | UR-PRC-02 |
| AC-05 | 소요 시간 | 소스 12개 기준 30초 이내 완료 | UR-NFR-01 |
| AC-06 | 부분 실패 내성 | 잘못된 주소를 하나 넣어도 나머지 정상 수집 | UR-COL-04 |
| AC-07 | 설정 반영 | 화면에서 키워드 추가 후 다음 실행에 반영 | UR-CFG-01, UR-NFR-07 |
| AC-08 | 비동기 실행 | 실행 버튼 클릭 후 1초 내 화면 응답, 상태가 갱신됨 | UR-EXE-02, 04 |
| AC-09 | 자동 실행 | 지정 시각에 개입 없이 메일 발송 | UR-SCH-01 |
| AC-10 | 인증 정보 분리 | 저장소에 계정 정보가 포함되지 않음 | UR-NFR-05, 06 |

**AC-01과 AC-04가 핵심이다.**
AC-01은 기존 기능을 대체했음을, AC-04는 기존보다 나아졌음을 증명한다.

## 부록 A. API 계약

**개발 첫날 확정한다.** 이것이 확정되어야 프론트가 목 서버로 병렬 작업할 수 있다.

### A.1 공통 규칙

| 항목 | 결정 |
|---|---|
| JSON 네이밍 | snake_case |
| 일시 형식 | ISO 8601, UTC (`2026-09-08T14:30:00Z`) |
| 목록 응답 | `{ total_count, page, items_per_page, items }` |
| 에러 응답 | `{ code, message, fields? }` |
| 인증 | 없음 (이번 릴리스) |

### A.2 상태 코드

| 상황 | 코드 |
|---|---|
| 조회 성공 | 200 |
| 생성 성공 | 201 |
| 실행 접수 | 202 |
| 삭제 성공 | 204 |
| 입력값 오류 | 400 |
| 없는 리소스 | 404 |

### A.3 엔드포인트

```
GET    /settings                     메일 제목·수신자·최대건수·키워드
PUT    /settings

GET    /feed-sources
POST   /feed-sources                 → 201
PUT    /feed-sources/{id}
DELETE /feed-sources/{id}            → 204

GET    /articles?page=&items_per_page=&keyword=&site=&from=&to=

POST   /collect                      → 202 { execution_id }
GET    /executions?page=
GET    /executions/{id}
```

